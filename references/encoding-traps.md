# 编码陷阱全集

日式视觉小说的文本层几乎每个环节都有一个「看起来能跑但结果是错的」的坑。
本文按出现频率排序，每条给出：症状 → 根因 → 判据 → 修法。

---

## 1. lead 字节翻转（bit0）

**症状**：直接按 SJIS 解码得到乱码，但按 `cp932` 解「一半对一半错」；或者文本能解出来，
但长句在特定字符处被切断，条数比预期多一倍。

**根因**：文件里的双字节字符，首字节翻转了 bit0。

```
原始 SJIS lead:  0x81 .. 0x9F,  0xE0 .. 0xFC
存储形式:        0x80 .. 0x9E,  0xE1 .. 0xFD     (lead ^ 1)
```

引擎加载时再翻回来。这是最老也最常见的一层混淆，目的是让文本区看起来不是纯 SJIS。

**判据**：probe 输出里同一编码下 `xor=1` 的 precision 明显高于 `xor=0`（本项目 97.9% vs 70.8%）。

**修法**：`"lead_xor": 1`。

**连带陷阱**：判断「这个字节是不是 lead」时，范围必须用**存储态**：

```python
# 错：漏掉 0x80 和 0xFD
LEAD = ((0x81, 0x9F), (0xE0, 0xFC))

# 对：放宽到覆盖两种 xor
LEAD = ((0x80, 0x9F), (0xE0, 0xFD))
```

漏掉 `0x80` 的后果很严重：`0x81 ^ 1 = 0x80` 是极常见的 lead，每个这样的字符都会切断一个长句。
本项目实测：漏掉后提取出 47889 条碎句（正确 22143 条），字节数还少了 15%（短段被 `min_chars` 丢弃）。

## 2. 用 `0x00` 填充空位

**症状**：每屏只显示第一行，句子在半截断掉，后面的行消失。文本内容本身是对的。

**根因**：`0x00` 在脚本格式里是**换行控制码**。等长注入时把空位补 `0x00`，
等于在每行后面插入了一串换行，把同一页后面的行推出了文本框。

**判据**：实机截图对照。本项目用 A/B 两版补丁（一版补 `0x00`，一版补 `A0 A1`）对比确认。

**修法**：补**全角空格**的存储形式。

| 目标编码 | 全角空格 | 存储形式（xor=1） |
|---|---|---|
| GBK | `A1 A1` | `A0 A1` |
| Big5 | `A1 40` | `A0 41` |
| SJIS | `81 40` | `80 41` |

`A0 A1` 两个字节都 ≥ 0x80，会被当作正文字符（翻回来是全角空格），不产生控制码。

**通用规则**：填充单元必须是「目标编码下合法、且解码后不可见、且不含控制字节」的双字节。
不确定时用全角空格，几乎总是安全的。

## 3. 半角 ASCII 打乱对齐

**症状**：数字和字母显示错位——`A` 变 `@`，`1` 变 `0`，`B` 变 `C`。中文字符正常。

**根因**：引擎按**固定 2 字节步进**解码并翻转首字节。半角 ASCII 只有 1 字节，
插入后后面所有字符的「首字节/次字节」角色全部错位一格，翻转就翻到了错误的字节上。

```
逻辑:  你 A 好
GBK:   C4 E3  41  BA C3        ← 'A' 只有 1 字节
步进:  [C4 E3] [41 BA] [C3 ..]  ← 全错
```

**修法**：编码前把 ASCII 全角化。

```python
def to_fullwidth(s):
    return ''.join(
        chr(ord(c) + 0xFEE0) if 0x21 <= ord(c) <= 0x7E
        else ('\u3000' if c == ' ' else c)
        for c in s)
```

全角 `A` 在 GBK 里是 `A3 C1`，2 字节，对齐正确。

**注意**：全角化会让长度增加。策略是「全角优先，超预算再退回半角」：

```python
fw = to_fullwidth(zh)
if len(encode(fw)) <= budget:
    use(fw)
elif len(encode(zh)) <= budget and len(encode(zh)) % 2 == 0:
    use(zh)          # 半角但长度偶数，仍然对齐
else:
    report_overflow()
```

## 4. 奇数长度

**症状**：和 #3 类似，但只在某些行出现；或整页从某一行开始全部错位。

**根因**：替换后的字节数是奇数，后续按 2 字节步进时错位。

**修法**：强制偶数长度。差 1 字节时把最后一个半角字符全角化（长度 +1），
或者补一个 pad 字节（会多出一个全角空格，通常可接受）。

`inject.py` 的 `force_even` 负责这件事，`odd` 计数必须为 0。

## 5. 字体字符集（GDI `TextOutA`）

**症状**：文本编码全对，但屏幕上仍是乱码，或者中文显示成方块。

**根因**：走 GDI 的 `TextOutA` 时，8 位字符串按「字体字符集（lfCharSet）」对应的代码页解释，
**不是**按系统 ACP。原版字体是 `SHIFTJIS_CHARSET (0x80)`，所以日文正常；
换成 GBK 字符串后，仍然按 SJIS 解释 → 乱码。

**修法**：改 exe 里创建字体的地方，把 `lfCharSet` 改成 `GB2312_CHARSET (0x86)`，
`lfFaceName` 改成中文字体。

定位方法：
1. 在 exe 里搜 `CreateFontA` / `CreateFontIndirectA` 的导入引用
2. 找到构造 `LOGFONTA` 结构的地方
3. `LOGFONTA` 布局：`lfHeight(4) lfWidth(4) lfEscapement(4) lfOrientation(4) lfWeight(4)
   lfItalic(1) lfUnderline(1) lfStrikeOut(1) lfCharSet(1) lfOutPrecision(1)
   lfClipPrecision(1) lfQuality(1) lfPitchAndFamily(1) lfFaceName(32)`
   —— `lfCharSet` 在偏移 23
4. 把 `0x80` 改成 `0x86`，把 `lfFaceName` 写成 `SimSun`

**注意**：`lfHeight` 为负值表示字符高度（`-12` = 12px）。中文字体在同样高度下视觉偏小，
可能需要把绝对值调大 1–2。

## 6. 文本区边界

**症状**：漏掉开头几行；或多提取出一堆垃圾条目。

**根因**：`region` 起点/末端不准。

**修法**

- 起点：宁可往前。往前多扫几个字节没有代价（扫描器只收合法 CJK run），
  往后则会漏文本。probe 已经按 `(first_run - 4) & ~3` 取整。
- 末端：必须精确。本项目末端写成 `0x1226F0` 时少了 20 条文本 / 6 页；改成 `0x122930` 后完全对齐。

**验证方法**：`strings` 的 `bytes` 总和 + 非文本区大小 ≈ 文件大小。
若有明显缺口，说明末端截断了。

## 7. 假名与汉字的判定

**症状**：probe 把日文文件判成 GB18030/GBK。

**根因**：宽 lead 的中文编码会把假名字节解成汉字，所以「合法字符数」偏向更宽的字符集。
本项目：gb18030 解出 349961 个合法字符，cp932 只有 332493 个 —— 但 gb18030 的假名数是 52，
cp932 是 246446。

**修法**：用**假名计数**（U+3040–U+30FF）作为日文判据。真日文脚本假名占比极高，
任何中文编码都还原不出来。只有假名数很低（< 50）时才退回用 precision 排序。

## 8. 字符集外字符

**症状**：某几条译文变成 `?` 或乱码。

**根因**：目标编码（GBK）里没有该字符。常见于 `♪`（U+266A）、`・`（U+30FB）、
某些特殊符号。

**修法**：预映射表。

```json
"fix": {
  "\u266a": "\uff5e",
  "\u266b": "\uff5e",
  "\u30fb": "\u00b7"
}
```

或者直接改写译文（`♪` → `～`）。

---

## 9. 逐字回退

**症状**：未翻译的行显示乱码。

**根因**：原文是 SJIS，目标编码是 GBK，字节不同，直接原样保留必然乱码。

**修法**：把未翻译的日文**逐字转成目标编码**；转不了的字符保留原始存储字节。
这样至少假名和汉字能显示（虽然读者看到的是日文），不会满屏乱码。
`inject.py` 的 `raw_kept` 统计的就是「保留原始字节的字符数」，正常应为 0 或极小。
