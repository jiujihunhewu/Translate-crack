# 完整流程手册

每个阶段给出：**目标 / 操作 / 通过判据 / 失败怎么办**。
判据不通过就不要进入下一阶段——后面的工作都建立在前面的正确性上。

---

## 阶段 0：取证

**目标**：拿到纯净原件，确认版本。

**操作**

```bash
mkdir -p work/mygame/orig
cp <游戏目录>/game.id work/mygame/orig/
md5sum work/mygame/orig/game.id
ls -l work/mygame/orig/
```

**判据**

- `orig/` 里是**未修改**的原件
- 记录了 md5 和文件大小

**失败怎么办**

如果用户手上只有「已装过补丁」的文件，要求他从安装镜像（iso/mds）或原始压缩包里重新解出原件。
拿打过补丁的文件当源，提取出来的会是乱码——本项目实测：对一个已汉化的 `.id` 再提取，得到 3223 条
「隘愠」之类的垃圾，因为文本已经是 GBK，按 SJIS 解当然失败。

**指纹**：在文本区起始处放一个特征字节序列，写进 `game.json` 的注释里。
本项目用 `0x41D04` 处的 `8249805b`（首行菜单文字的存储形式）。每次构建前校验一次，
就能防止「误把已打补丁的文件当源」这种事故。

## 阶段 1：编码探测

**目标**：确定 `encoding` / `lead_xor` / `region` / `page_break` 四个参数。

**操作**

```bash
python scripts/probe.py work/mygame/orig/game.id --top 8
```

**判据**

- 最优假设的 `precision` > 90%
- 若是日文游戏，`kana` 数量应在数万以上（本项目 246446）

**为什么看假名而不是字符总数**

宽 lead 的中文编码（gb18030、gbk）会把假名的字节解成汉字，所以「合法字符数」反而偏向**更宽**的字符集。
本项目实测：gb18030 解出 349961 个「合法字符」，cp932 只有 332493 个，但 gb18030 的假名数是 52，
cp932 是 246446。**假名数是决定性判据**——真日文脚本里假名占比极高，任何中文编码都还原不出来。

**`lead_xor` 怎么定**

看同一编码下 xor=0 和 xor=1 的 precision 差距。本项目 cp932 xor=1 是 97.9%，xor=0 只有 70.8%，
一目了然。如果两者接近，说明该文件没有做 bit0 翻转，取 xor=0。

**`region` 怎么定**

probe 给出的区间是从「第一个长文本 run」往前取整到 4 字节边界。宁可往前取：
起点早了只是多扫几个字节（扫描器会跳过非文本），起点晚了会漏掉开头几行。

末端必须精确到文件尾或文本区结束。本项目一开始把末端写成 `0x1226F0`，结果少提取 20 条文本、
少 6 页——**差 768 字节就会丢 20 条**，所以要用「最后一个长 run 的结束」而不是估算。

**`page_break` 怎么定**

probe 输出的「candidate separators」是按频次排序的 4 字节间隙模式。但**不要直接采信第一条**：
本项目 probe 报 `80638063`（6881 次），实际正确的页分隔符是 `03000200` / `01000200`。
前者是文本内部的常见字符对，后者才是结构标记。

判据：把候选逐个代入，看 `pages` 的 `lines/page` 分布。合理的视觉小说应该是
「1–5 行/页」为主，且 2–4 行的页占大头。如果 90% 的页只有 1 行，说明分隔符选错了（切太碎）。

**失败怎么办**

- 完全扫不出文本 → 文件被压缩或加密，先找解包器（`arc`/`pak`/`dat` 容器），或看 exe 里的解压函数
- 有文本但 precision 低 → 试试 `utf-16-le`，或该文件是「文本+索引」混合结构，需要先分离
- 页分隔符找不到 → 用 `line_break` 单参数先跑通提取，分页可以后补（提取不依赖分页）

## 阶段 2：提取

**目标**：拿到 `strings.json`（每条文本的偏移/长度/原文）和 `pages.json`（分页结构）。

**操作**

```bash
python scripts/extract.py work/mygame/game.json work/mygame/orig/game.id -o work/mygame/data
```

**判据**

- `strings` 数量稳定（重跑两次结果一致）
- `bytes` 总和 + 非文本区 ≈ 文件大小
- 抽样检查前 20 条：是完整句子，不是半个词

**关键：分页只能用「文本段之间夹着什么」来判定**

不要试图按固定帧长解析。多数引擎的页头/页尾参数里含有看起来像合法 SJIS 的字节，
按固定偏移解析一定会被参数吃掉对齐。正确做法是先把文件切成 `text` / `gap` 交替的 run 序列，
再看 gap 的内容决定是「换行」「翻页」还是「软分隔」。

本项目实测：`gap == 0000` 是页内换行，`gap` 含 `03000200` 或 `01000200` 是翻页，
其它 gap 当软分隔。这样得到 14714 页，和引擎实际表现一致。

**失败怎么办**

- 条数明显偏少 → 检查 `lead` 字节范围。**必须包含 0x80 和 0xFD**（xor=1 时 0x81→0x80、0xFC→0xFD）。
  本项目最初把范围写成 `0x81-0x9F, 0xE0-0xFC`，结果长句在每个 0x80 处被切断，
  提取出 47889 条碎句（正确值是 22143 条），字节数还少了 15%。
- 条数明显偏多 → `min_chars` 设太小，调到 2 或 3
- 译文注入后命中率低 → 行首偏移算错了。本项目 `pages.py` 里 `cur['lines'][-1][0]` 只在首次置值，
  导致后续行的偏移全是错的，命中率只有 1507/3342（45%）。修好后是 22143/22143（100%）。

## 阶段 3：翻译

**目标**：产出 `trans/script_NNN.json`，键为偏移或原文。

**格式**

```json
{
  "041D04": "观看片头",
  "041D18": "不观看片头",
  "今日は休みか……。": "今天休息吗……"
}
```

优先用偏移键（`'%06X' % offset`，大写十六进制），唯一且不受原文修改影响。

**判据**

- 每条译文的**目标编码字节数** ≤ 原槽位长度
- 不含目标字符集外的字符（`♪` `・` 等要预映射）

**超预算怎么办**

不要截断。`inject.py` 会把它列进 `over` 并回退原文，返回值 2。做法：
1. 看 `over` 列表里的 `[need > budget]`
2. 把这几条译文改短（中文通常能比日文短 30%）
3. 重跑到 `over 0`

**编码链路**（本项目踩过的坑，务必确认自己面对的引擎属于哪种）

```
文件存储  = 逻辑字节流，每个双字节字符的 lead 翻转 bit0
引擎加载  = 再翻一次 -> 得到逻辑字节流 -> 交给 TextOutA 按系统 ACP 解码
```

所以逻辑字节流必须直接是目标编码（GBK），写入前预翻转即可。

## 阶段 4：注入

**目标**：产出和原文件**等长**的补丁文件。

**操作**

```bash
python scripts/inject.py work/mygame/game.json work/mygame/orig/game.id \
       work/mygame/trans/script_001.json -o work/mygame/build/game.id
```

**判据**

```
translated  = 译文条数
kept        = 0          ← 未翻译条数，应为 0
over        = 0          ← 超预算条数，必须 0
odd         = 0          ← 奇数长度条数，必须 0
```

**四个必须处理的陷阱**

1. **pad 不能是 `0x00`**：`0x00` 是换行控制码。用 `A0 A1`（全角空格的存储形式）。
   本项目最初用 `0x00` 补，实机截图显示「每屏只显示第一行、句子断掉」，A/B 对照后才定位到。
2. **半角 ASCII 要全角化**：引擎按偶数位置翻转 bit0 解码，半角字符只有 1 字节会打乱对齐。
3. **长度要为偶数**：奇数长度会让后续字符错位。
4. **超预算不能截断**：回退原文并报告。

## 阶段 5：校验

**目标**：确认补丁没破坏任何非文本数据。

**操作**

```bash
python scripts/verify.py work/mygame/game.json work/mygame/orig/game.id \
       work/mygame/build/game.id --trans work/mygame/trans/script_001.json
```

**判据（全部必须满足）**

```
size                same
non-text drift      none        ← 最关键
undecodable         0
translation coverage 100%
```

**`non-text drift` 不为 none 说明什么**

说明文本槽位表算错了，注入器改到了代码区/索引区。**这种情况下打包出去会直接让游戏崩溃或行为异常。**
必须回到阶段 2 重新核对 `region` 和 `min_chars`，不能靠「看起来能跑」蒙过去。

**冒烟测试**

静态校验过了还要实机跑。自动点几百次确认不崩溃：

```python
# 用 pyautogui / pydirectinput 循环点击，统计崩溃次数
# 本项目实测 620 次点击 / 464 次推进 / 0 崩溃
```

## 阶段 6：打包

**目标**：产出可分发、可回滚的补丁包。

```bash
python scripts/package.py work/mygame/game.json --orig work/mygame/orig \
       --build work/mygame/build --out work/mygame/patch
```

产物：

```
patch/
  files/            汉化后文件
  backup/           原版（卸载用，必须有）
  install.bat/.sh   安装
  uninstall.bat/.sh 还原
  README.txt        说明 + md5 清单
  manifest.json     机器可读清单
```

**判据**

- `backup/` 里的 md5 和阶段 0 记录的一致
- 安装 → 运行 → 卸载 → 再运行，两步都正常
